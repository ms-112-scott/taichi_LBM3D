## P0 地基校正

### P0.1 tau_f 公式驗證

**現況**：`Single_phase/LBM_3D_SinglePhase_Solver.py:127` 用 `self.niu/3.0+0.5`，而 repo 裡其他六個檔案（含幾乎同一份的 `Phase_change/LBM_3D_SinglePhase_Solver.py`）全用 `3.0*niu+0.5`。改動來自 commit `a0461be`，標題就叫 fix tau calculation。

**標準關係**（lattice units）：

```latex
\nu = c_s^2\left(\tau - \tfrac{1}{2}\right) = \frac{\tau - 0.5}{3}
\quad\Longrightarrow\quad
\tau = 3\nu + 0.5
```

現行公式反推：設 `niu = 0.1` → `tau_f = 0.5333` → ν_實際 = (0.5333−0.5)/3 = **0.0111 = niu/9**。

**驗證方法**：跑 `example_poiseuille_flow.py`（與那個 commit 同時加入）。兩平板間 Poiseuille 流的解析解是拋物線：

```latex
u(y) = \frac{G}{2\nu}\left(\left(\tfrac{H}{2}\right)^2 - y^2\right)
```

G 是外力（`fx`），H 是通道寬。量測中心線 u_max 與解析值比對。

| 觀察 | 結論 |
| --- | --- |
| 誤差 < 1% | 現行公式對，repo 其他檔案錯 |
| u_max 約為解析值的 **9 倍** | 現行公式錯（ν 小 9 倍 → 流速大 9 倍） |
| 誤差 5–20% 且隨 τ 變化 | 邊界條件問題，另外查 |

中間那一欄是預期結果。9 倍是很好認的訊號，不會跟數值誤差混淆。

### ❗ 重大修正：Poiseuille 測試會假性通過

實際讀完 `colission()` 之後發現，`commit a0461be` **同時改了兩個地方**，而它們的錯誤會在外力驅動流裡精確抵消。

**第 236 行的 Guo 外力項**：

```python
f_guo += w[l]*((e_f[l]-v).dot(f)/3.0 + (e_f[l].dot(v)*(e_f[l].dot(f)))/9.0)*M[s,l]
```

標準 Guo 外力應該是 **乘** 1/cₛ² = 3 與 1/cₛ⁴ = 9，這裡卻是**除**以 3 與 9。主導項比值 = (1/3)/3 = **1/9**，也就是外力只注入了 F/9。

搭上 `tau_f = niu/3 + 0.5` 得到 ν = niu/9，兩個錯誤在 Poiseuille 裡完全抵消：

```latex
u_{\max} = \frac{G/9}{2\,(\nu/9)}\left(\frac{H}{2}\right)^2
= \frac{G}{2\nu}\left(\frac{H}{2}\right)^2
```

**結果是正確的。但 ν 實際小 9 倍。**

這代表我原本設計的 P0.1 測試**抓不到這個 bug**。更糟的是它會給你一個「通過了」的訊號，讓你帶著錯的 ν 走到 P4。

### 修正後的 P0.1 測試設計

要測出 ν，必須用**不含外力**的案例：

| 測試 | 驅動方式 | 能否抓到 ν 錯誤 |
| --- | --- | --- |
| Poiseuille（原計畫） | 外力 | ❌ **抵消，假性通過** |
| **衰減剪切波** | 無（初始條件） | ✅ 直接量 ν，最乾淨 |
| **Lid-driven cavity** | 速度邊界 | ✅ ν 錯 → 實際 Re 錯 9 倍 |
| 定壓驅動多孔流 | 壓力邊界 | ✅ 滲透率偏高 ~9 倍 |

**新的 P0.1 主測試：衰減剪切波。** 初始場 u_x(z) = U₀ sin(2πz/L)，無外力、週期邊界，振幅應該按解析解衰減：

```latex
U(t) = U_0 \exp\left(-\nu k^2 t\right), \qquad k = \frac{2\pi}{L}
```

量測衰減率直接反推 ν，與 `niu` 比對。**一個數字就能定案：比值是 1 還是 1/9。** 這個測試五十行程式，跑幾秒鐘。

### 這件事的含意比一個 bug 大

舊版（被註解掉的 `GuoF`）外力項沒有 ×3 與 ×9，實際是 F/3；搭 `tau = 3ν+0.5`（ν 正確），Poiseuille 會差 3 倍。新版把外力改成 F/9、ν 改成 ν/9，把 Poiseuille 「修好了」。

**兩個版本都是錯的**，新版只是恰巧地在一個測試上抵消。所以 P0.1 不是「選一個公式」，而是**兩個地方都要修**：

- `tau_f = 3.0*niu + 0.5`
- Guo 外力項的 `/3.0`、`/9.0` 改成 `*3.0`、`*9.0`

改完之後 Poiseuille 會先壞掉（變成原來的 9 倍），兩個都改對才會回到正確值——**這個「先壞後好」的過程本身就是驗證**。

### P0.2 ghost mode 鬆弛率解耦

改兩行，換高 Re 穩定性。這是目前 repo 裡和建築風用途落差最大的一處。

**現況**（`init_simulation()` 第 130 行）：

```
s_v     = 1.0 / tau_f
s_other = 8.0 * (2.0 - s_v) / (8.0 - s_v)
```

這是 TRT 的 magic parameter（Λ = 3/16），讓 bounce-back 壁面位置在 Poiseuille 流下精確落在格點中間——對**多孔介質**（repo 的原始用途）是很好的選擇。

**問題在 τ→0.5 時**：

| τ | s_v | s_other | ghost mode 衰減時間 |
| --- | --- | --- | --- |
| 1.00 | 1.000 | 1.143 | ~1 步 |
| 0.60 | 1.667 | 0.421 | ~2 步 |
| 0.51 | 1.961 | 0.052 | ~19 步 |
| 0.5003 | 1.9988 | **0.0016** | **~625 步** |

### ❗ 修正：這不是「ghost modes」，是 TRT 結構

我之前寫「index 2, 4, 6, 8, 10, 12, 16, 17, 18 全部吃 `s_other`」是**錯的**。實際的 `S_dig`（第 131 行）：

| 鬆弛率 | index | 矩 |
| --- | --- | --- |
| `0`（守恆） | 0, 3, 5, 7 | ρ, j_x, j_y, j_z |
| `s_v` | 1, 2, 9, 10, 11, 12, 13, 14, 15 | e, ε, 剪應力與 π |
| **`s_other`** | **4, 6, 8, 16, 17, 18** | **q_x, q_y, q_z, m_x, m_y, m_z** |

`s_other` 只管**奇矩**（odd moments）——能量通量 q 與三階 ghost m。偶矩全部走 `s_v`。

這就是標準的 **TRT 結構**：偶矩一個鬆弛率 s⁺、奇矩一個 s⁻，並且：

```latex
\Lambda = \left(\frac{1}{s^+}-\frac{1}{2}\right)\left(\frac{1}{s^-}-\frac{1}{2}\right) = \frac{3}{16}
```

我實際代入驗算過：τ = 1.0 / 0.8 / 0.6 / 0.51 / 0.5003 五組全都得到 **Λ = 0.1875 恆定**。`s_other = 8(2−s_v)/(8−s_v)` 這個公式就是為了鎖住 Λ = 3/16 而存在的。

**Λ = 3/16 是有意義的選擇**：它讓 bounce-back 壁面在 Poiseuille 流下精確落在半格處，而且**壁面位置不隨 τ 漂移**。對多孔介質（壁面面積極大）這是正確的工程決定。這是 repo 目前最值得保留的設計。

### 修正後的改法：不是「設成 1.0」

我之前建議「把 ghost 鬆弛率固定在 1.0，等於 regularized LBM」——**這個建議是錯的**，而且會弄壞 repo 目前做對的事。

把 `s_other` 改成常數 1.0 之後，Λ 不再固定，而是變成 Λ = (τ−0.5)/2 隨 τ 漂移。後果：**壁面位置會隨黏度變動**。P5 要掃 8–16 個風向、P4 的 LES 還會讓 τ 逐格變化——那會變成每一格的有效建築表面都在不同位置。

**真正的問題是什麼**：Λ 固定在 3/16 時，τ→0.5 強迫 s⁻ → 0。奇矩（q、m）幾乎不被鬆弛，只被搬運不被阻尼。這是真的風險，但範圍比我原本寫的窄（只涉及六個奇矩，不是九個）。

兩個正確的選項：

| 選項 | 做法 | 代價 |
| --- | --- | --- |
| **A. 調 Λ** | 保持 TRT 結構，把 Λ 從 3/16 降到較小值 | 壁面位置不再精確在半格，換高 Re 穩定性 |
| **B. 換成正交 MRT** | 把 M 換成標準 d'Humières 基底、重算 meq，鬆弛率全部獨立設 | 工作量大一點，但之後所有文獻參數都能直接用 |

**建議選 B，而且提前到 P0 的第一件事。** 理由在 P4 那節講：現行的 M 是非正交基底，有三對矩被綁在一起，而 LES 恰好需要拆開其中一對。不先處理，P4 的 LES 會帶進一個隨空間變化的寄生耦合項。

**驗證方式**：換成正交 M 之後，先用相同的有效鬆弛率跑一次，確認與現行版**逐格一致**（差異應在浮點誤差級）。這證明換基底沒改變物理，之後才能安心調鬆弛率。

先不要動：多孔介質模式維持 Λ = 3/16，作為可切換選項保留。

**驗證**：同一個 cavity 案例，把 τ 從 0.8 逐步降到 0.505，記錄改前改後各自在哪個 τ 發散。

**保留舊路徑**：多孔介質模式仍用舊公式，改成可切換旗標。未來可能要做多孔建材的題目。

### P0.3 幾何注入

`init_geo()` **已經在用 `from_numpy`**：

```python
def init_geo(self, filename):
    in_dat = np.loadtxt(filename)
    in_dat[in_dat > 0] = 1
    in_dat = np.reshape(in_dat, (self.nx, self.ny, self.nz), order='F')
    self.solid.from_numpy(in_dat)
```

所以只要加一個重載：

```python
def init_geo_from_array(self, arr):
    self.solid.from_numpy(arr.astype(np.int8))
```

**坑：`order='F'`。** 你從體素化出來的陣列必須是 `(nx, ny, nz)` 且 `solid[i,j,k]` 對應 x→i, y→j, z→k。搞錯會得到轉置的建築，而且**看起來很合理**。用不對稱盒子（x 10 格、y 20 格）一眼就能抓到。

### P0.4 驗證套件與單位換算

做成可重跑的腳本，**每次改 kernel 都跑**。這套東西在 P6 改寫 in-place streaming 時會救你一命。

| 案例 | 對標 | 檢查量 | 可接受誤差 |
| --- | --- | --- | --- |
| Poiseuille | 解析解 | u_max、剖面形狀 | < 1% |
| Cavity Re=100 | Ghia et al. 1982 | 中心線 u(y)、v(x) | < 3% |
| Cavity Re=400 | Ghia et al. 1982 | 同上 | < 5% |
| Cavity Re=1000 | Ghia et al. 1982 | 同上 | < 8% |

**單位換算模組**（獨立 `units.py`）：

```latex
\Delta t = \frac{u_{\text{lat}} \cdot \Delta x}{u_{\text{ref}}}, \qquad
\nu_{\text{lat}} = \frac{u_{\text{lat}} \cdot N_{\text{char}}}{Re}, \qquad
\tau = 3\nu_{\text{lat}} + 0.5
```

內建三個警告：

| 條件 | 含義 | 訊息 |
| --- | --- | --- |
| Ma = u_lat·√3 > 0.2 | 壓縮性誤差過大 | 降 u_lat 或加大 Δx |
| τ < 0.501 | 無 LES 時必炸 | 需要湍流模型（P4） |
| τ > 1.5 | 過度耗散，結果失真 | 提高 Re 或加密網格 |

**永遠不要讓物理單位漏進 kernel。** 這個模組在 P2 被自動解析度推導呼叫，P5 的多風向批次也靠它算每個案例要跑幾步。

## P1 最小垂直切片（上）

P1 的唯一目的是**消除整個專案最大的技術未知**：taichi 能不能活在 Rhino 8 的嵌入式 Python 裡。醜、慢、會卡都可以。

### P1.1 環境測試：最優先的 30 分鐘

在寫任何其他程式之前先做這件事。

| 項目 | 狀況 |
| --- | --- |
| Rhino 7 GHPython | IronPython 2.7，**跑不了 taichi**（需 CPython + numpy + LLVM） |
| Rhino 8 Windows | 內建 CPython 3.9，支援 `# r:` 自動安裝 |
| taichi CUDA backend | 只需 NVIDIA **驅動程式**，不需完整 CUDA toolkit |
| 首次安裝 | taichi wheel 約 300 MB，要等 |

```python
# r: taichi
import taichi as ti
ti.init(arch=ti.gpu)

@ti.kernel
def probe() -> ti.f32:
    s = 0.0
    for i in range(1000):
        s += 1.0
    return s

result = probe()          # 應該是 1000.0
```

要看三件事：`import` 過不過、`ti.init(arch=ti.gpu)` 有沒有退回 CPU、kernel 算出來的值對不對。並且**計時**：第一次執行包含 JIT 編譯，預期 2–10 秒。

| 結果 | 含義 | P1 怎麼走 |
| --- | --- | --- |
| **A** import 成功、GPU 成功 | 最好的情況 | in-process，P1 可以偷懶 |
| **B** import 成功、GPU 退回 CPU | 驅動或環境問題 | 先查驅動；確定無 GPU 則格數降到 1M |
| **C** import 失敗或 Rhino 崩潰 | 嵌入式直譯器裝不下 | 立刻切 subprocess |

**就算拿到 A，最終架構還是 subprocess。** 理由跟效能無關，是崩潰隔離：taichi kernel 遇到 NaN 或越界可能直接 hard crash 整個行程，在 Rhino 內就是 Rhino 陪葬。一個會弄丟建築師兩小時工作的工具，算得再快也沒人敢用。

A 的意思是「P1 可以跳過 IPC」，不是「架構定了」。C 反而是把 P3 的工作提前做掉。

**要記錄的數字**：`ti.init()` 耗時、首次 kernel JIT 耗時、第二次呼叫耗時。這三個數字決定 P3 的預熱策略要多積極。

### P1.2 求解器驅動 API

現有 class 的介面已經夠用，P1 不需要改寫。

| 呼叫 | 用途 | 時機 |
| --- | --- | --- |
| `LB3D_Solver_Single_Phase(nx,ny,nz)` | 建立、配置記憶體 | 一次 |
| `solid.from_numpy(arr)` | 注入幾何 | init 前 |
| `set_viscosity(niu)` | 黏度 | **必須在 init 前** |
| `set_force([fx,fy,fz])` | 外力 | **必須在 init 前** |
| `set_bc_vel_x0([vx,vy,vz])` | 入流速度 | init 前 |
| `init_simulation()` | 算 tau、建表、初始化場 | 一次 |
| `step()` | 跑一步 | 迴圈 |
| `v.to_numpy()` | 取速度場 (nx,ny,nz,3) f32 | 需要時 |
| `get_max_v()` | 發散監控 | 每 N 步 |

**陷阱一：參數必須在 `init_simulation()` 之前設。** `init_simulation()` 裡才從 `self.niu` 算 `tau_f`、從 `fx/fy/fz` 填 `ext_f`。init 之後再呼叫 `set_viscosity()` **完全沒效果，而且不會報錯**——你會以為在掃參數，實際上每次都跑同一組。

**陷阱二：`force_flag` 是編譯期常數。** `colission()` 裡用 `ti.static(self.force_flag==1)` 包住力項，這個判斷在 kernel 編譯時就被展開掉了。不只是「要在 init 前設」，而是「一旦 kernel 編譯過就不能切換有力／無力模式」。**P1 不要碰**，先記下來。

**需要加的方法**：

```python
def velocity_numpy(self):
    return self.v.to_numpy()   # (nx, ny, nz, 3) float32
```

取代 `export_VTK()`。順帶一提：現行 `export_VTK()` 呼叫了**三次** `self.v.to_numpy()`（每個分量一次），每次都是完整的 GPU→CPU 拷貝。別照抄這個寫法。

**`to_numpy()` 是阻塞同步呼叫。** 每步都叫會讓 GPU pipeline 停頓。P1 沒差，但要養成習慣：**每 k 步才拷一次**，k 寫成參數。P3 改成 GPU 粒子之後，這個參數直接變成「回傳頻率」旋鈕。

### P1.3 資料契約（P1 唯一要認真做的設計）

P1 其他部分都可以醜，這一項不行。它是**求解器與顯示的唯一接面**：後端從 taichi 換 CUDA、傳輸從同行程換共享記憶體、顯示從 GH 預覽換 DisplayConduit——**這個格式都不用改**。

```python
PARTICLE_DTYPE = np.dtype([
    ('pos',   np.float16, 3),   # 正規化座標 [0,1]，非公尺
    ('speed', np.uint8),        # 速度大小 / speed_max * 255
    ('flags', np.uint8),        # bit0: 本幀是否重生
])                              # 8 bytes / particle
```

標頭：`version` (u32)、`n_particles` (u32)、`frame_id` (u32)、`speed_max` (f32)、`bbox_min`/`bbox_max` (f32×3)。

50,000 粒子 = **400 KB/frame**。

**為什麼座標要正規化到 [0,1]**：float16 尾數只有 10 bits，相對精度約 0.05%。直接存公尺的話：

| 尺度 | 域長 | f16 絕對精度 | 相當於格數 |
| --- | --- | --- | --- |
| 都市 | 1500 m | 0.73 m | 0.19 格 |
| 建築 | 300 m | 0.15 m | 0.16 格 |
| 室內 | 20 m | 0.01 m | 0.19 格 |

正規化後精度變成**與尺度無關**的固定 0.0005 域長，而且同一套顯示程式不用為不同尺度調參數。f16 在 65504 以上會溢位，正規化順便把這個風險一併消掉。

**P1 怎麼用**：同行程，「傳輸」就是把這個 numpy 陣列從函式回傳。**但就是要用這個 dtype。** 不要因為「P1 反正在同一個行程」就回傳 float32 的 (N,3) 陣列。

### P1.4 GH 元件結構與狀態保存

P1 用**單一元件**。三元件拆法是 P2 的事，現在拆只會把還不確定的介面凍死。

| 輸入 | 型別 | 說明 |
| --- | --- | --- |
| `Run` | bool | 踩一下跑 N 步 |
| `Reset` | bool | 重建求解器 |
| `Steps` | int | 每次踩跑幾步 |
| `NumParticles` | int | 粒子數 |
| **輸出** |  |  |
| `Points` | Point3d[] | 粒子位置 |
| `Speeds` | float[] | 上色用 |
| `MaxV` | float | 發散監控 |
| `Info` | string | 步數、耗時、backend |

幾何寫死在程式裡，**不接 Rhino 幾何輸入**。一接就會被拉進體素化，而體素化是 P2 最大的工程項。

**狀態保存的真坑**：GH 的 dataflow 模型是「每次 solve 重新計算」，但求解器必須**跨 solve 存活**——它持有幾 GB 的 GPU 記憶體。

不要依賴 module-level global。用 `scriptcontext.sticky`，以元件的 InstanceGuid 當 key：

```python
import scriptcontext as sc

key = "lbm_" + str(ghenv.Component.InstanceGuid)
if Reset or key not in sc.sticky:
    sc.sticky[key] = make_solver(nx, ny, nz)
solver = sc.sticky[key]
```

用 InstanceGuid 而不是固定字串，是因為你一定會複製一份元件來比較兩組參數。固定 key 的話兩個元件共用同一個求解器，結果互相污染，而且症狀非常難懂。

> `ghenv` 在 Rhino 8 的 Python 3 元件仍然提供，但實作時先確認；若 API 有出入就改用手動指定的 key，機制一樣。

**VRAM 洩漏比狀態保存更危險。** taichi 的 field 沒有單獨釋放的 API，只能 `ti.reset()` 整個炸掉。每按一次 Reset 就新建一個 solver 的寫法會一路吊 GPU 記憶體。

兩個解法，**第二個才是對的**：

1. Reset 時先 `ti.reset()` 再重建——可行，但 JIT 要重跑
2. **依最大網格配置一次，之後只換內容不重配**——改幾何就重填 `solid`，改參數就重跑 `init()`

第二個寫法在 P1 看起來多餘（網格寫死 64³），但它直接就是 P3 熱啟動的底層機制。

**P1 刻意違反了一條架構規則**：「GH 絕不參與每幀」，但 P1 就是同步跑在 GH solve 裡。這是故意的——P1 不是架構，是切片；測的是鏈路通不通，不是順不順。

### P1.5 粒子平流與顯示

**為什麼 P1 用 CPU**：GPU 粒子 kernel 是 P3 的工作。P1 用 numpy 在 CPU 上算，1000 顆就好——這段邏輯在 CPU 上寫一次比較容易除錯，而且之後移植到 taichi kernel 時已經有一個知道答案對的版本可以對照。

**Trilinear 插值**：不做插值直接取最近格點的話，粒子會有明顯的網格感——一格一格跳。步驟：正規化座標 → `i = floor(x*nx)` 與小數部 `fx = x*nx - i` → 八個鄰居加權平均。numpy 向量化做完整批，**不要寫 Python 迴圈**。

**粒子的 dt 是視覺參數，不是物理參數。** 如果用 LBM 的 Δt，粒子每步只移動 u_lat = 0.05 格，要二十步才跨一格，看起來像沒在動。把它當成獨立的顯示旋鈕（典型值：每幀移動 0.5–2 格）。這也是 P3 「次步平流」能成立的原因——粒子時間本來就跟模擬時間脫鉤。

**重生邏輯**（沒這段畫面會變空）：

| 條件 | 原因 | 處理 |
| --- | --- | --- |
| 飛出計算域 | 正常出流 | 在入流面重新播種 |
| 進入 solid 格 | 插值跨過壁面 | 立刻重生 |
| 連續 k 步 \|v\| < 閾值 | 卡在死水區 | 累計計數器 |

第三個最容易漏。建築背風面的回流區會把粒子困住，慢慢地所有粒子都累積到那裡，流場的其他地方變空。播種位置 P1 就用入流面隨機——比全域隨機好看，而且更快看出流場結構。

**顯示**：元件輸出 `Point3d` list 接到 GH 的 Point 參數。想上色就把 `Speeds` 接進 Gradient 再接 Custom Preview——**用 GH 現成元件，不要自己寫**。

這裡會很慢（1000 顆就能感覺到），那正是 P3 存在的理由。**卡不是問題，是資料**——記下 1000 / 5000 / 20000 顆各自的幀率，P3 要拿這些數字證明自己改對了。

## P2 幾何與尺度系統

### P2.1 體素化

本階段最大的工程量，佔 20–30%。

**基本演算法：Z 方向 ray-stabbing parity test。** 每個 (x,y) 欄位射一條射線，用 `Intersection.MeshLine` 取得排序交點，配對填充。複雜度從 O(nx·ny·nz) 降到 O(nx·ny)。

逐點 `Mesh.IsPointInside` 測 800 萬格是不可能的，每次呼叫都要做一次完整的空間查詢。

**真正的問題：建築師的 mesh 不封閉。** 漏洞、翻面、重疊面、自交——parity test 遇到這些會產生**條紋狀錯誤**（整根柱子全實或全空）。

| 路徑 | 適用 | 缺點 |
| --- | --- | --- |
| parity test | 封閉乾淨 mesh | 破面就崩 |
| 表面光柵化 + flood fill | 破面容忍高 | 需加厚 1 格，薄牆可能變厚 |

**實作順序**：先跑封閉性檢查，決定走哪條路徑，並把結果告知使用者。不要默默切換——使用者需要知道自己的模型有問題。

**效能目標**：8M cells < 5 秒。超過這個，每次改建築都要等，互動感就沒了。

**測試資料要用真實案子**，不要用自己做的乾淨模型。自己做的模型永遠是封閉的，測不出問題。

### P2.2 尺度系統

**推導方向要反過來**：

```
分析類型 → Δx（由要解析的特徵決定）
       → N = V/Δx³
       → 告訴使用者記憶體需求與預估時間
```

Δx 量化到 0.02 / 0.05 / 0.1 / 0.25 / 0.5 / 1 / 2 / 5 m。量化後要**反推實際格數並確認沒超預算**——往下量化會讓格數暴增（三次方）。

**品質閘**：

| 尺度 | 關鍵特徵 | 最低格數 |
| --- | --- | --- |
| 都市 | 最窄街道寬 | 4 |
| 建築 | 最窄建築尺寸 | 10 |
| 室內 | 最小開口尺寸 | 5 |

**無效輸出鎖定**：Δx > 2 m 時鎖掉行人風輸出。z = 1.5 m 落在第一層格心以下，那個數字**物理上不存在**。不管介面上畫得多漂亮，使用者一定會拿去用。

### P2.3 邊界條件

**ABL 入流剖面**。現有 `set_bc_vel_x0()` 只能設均勻速度，要改成逐格向量場：

```latex
u(z) = u_{\text{ref}} \left(\frac{z}{z_{\text{ref}}}\right)^{\alpha}
```

α 從 0.14（開闊）到 0.33（市區）。參數化，不要寫死。

> 台灣的地況分類與 α 值應該查當地耐風規範，不要直接用國際教科書的數字。

地表粗糙度 z₀ 也要參數化，P5 的地況轉換會用到同一個值。

### P2.4 GH 元件拆分

| 元件 | 輸入 | 輸出 |
| --- | --- | --- |
| `WindDomain` | 幾何、分析類型、預算 | domain 規格物件 + 品質報告 |
| `WindSolve` | domain、風速、風向、步數 | solver handle |
| `WindResult` | solver handle | 速度場、粒子、切面 |

拆開的理由：`WindDomain` 可以單獨跑來檢查解析度（不用等模擬）；未來參數化最佳化只需要重跑 `WindSolve`。

**快取 key 現在就要決定。** P5 的多風向批次靠它避免重跑，參數化最佳化更靠它。key = 幾何 hash + 參數 hash；幾何 hash 要在**體素化之後**算（對體素陣列而不是原始 mesh），否則 mesh 的細微改動（重新劃分但形狀相同）會讓快取失效。

**參數 schema**：一份 JSON schema 描述所有模擬參數。未來 UI 可以自動生成，批次與最佳化也直接套用同一份。

## P3 即時顯示層

### P3.1 GPU 粒子平流 kernel

把 P1 的 CPU 版移到 taichi kernel。關鍵是平流對**全解析度場**做 trilinear 插值，不是對降採樣過的場。

成本核對：50k 粒子 × 8 次 memory fetch = 40 萬次，相對於 8M cells × 19 = 1.52 億次，只佔 **0.26%**。沒有隱藏成本。

驗證：用相同種子與相同速度場，與 P1 的 CPU 版逐粒子比對。先測單步，再測一百步的軌跡漂移。

### P3.2 獨立行程與共享記憶體

負載降到 350 KB/frame 之後，local socket（21 MB/s）也撐得住。但共享記憶體仍然更好：零拷貝、零序列化、延遲 < 0.1 ms vs socket 的 ~1 ms。工程量差距不大。

**Ring buffer 設計**：3 格輪流寫，一個 atomic write index。consumer 永遠讀「不是正在寫的那格中最新的」。

完全無鎖，**producer 永遠不會被 consumer 拖慢**——這點很重要，否則 Rhino 卡一下會反過來拖慢模擬。

**生命週期**：worker 要加 watchdog（parent PID 消失就自殺），GH document 關閉時確實 kill。殘留的 worker 會一直吃 GPU 記憶體，而且使用者不會知道。

### P3.3 C# DisplayConduit

**三個硬規則**：

1. **GH 絕不參與每幀**。元件只當控制器，畫面由 conduit 自己重繪，完全繞開 dataflow。
2. **幾何建立只能在 UI thread**。RhinoCommon 基本上不是 thread-safe；worker 只產生 raw float array，轉成幾何要 `RhinoApp.InvokeOnUiThread`。
3. **所有 taichi 呼叫固定在同一條執行緒**。CUDA context 綁定在建立它的執行緒。

**繪製**：一個 `PointCloud`（帶 per-point color），一次 `DrawPointCloud`。絕不迴圈畫 `DrawPoint`——**瓶頸是 draw call 數量，不是頂點數**。

**語言分工**。這個階段開始出現 C#，理由是 Python ↔ RhinoCommon 的 marshalling 成本：在 GHPython 裡迴圈建 50,000 個 `Point3d`，每幀要花數百毫秒，比模擬本身還慢。C# 裡跑 5 萬次迴圈是 sub-millisecond。

分工：Python/taichi 負責模擬與粒子，C# 負責體素化、顯示、IPC。

### P3.4 時間插值與自動降級

**CPU 端次步平流**。GPU 還沒給新場之前，粒子用手上最新的速度場自己繼續走。粒子軌跡本來就是連續的，這在物理上也說得通（速度場在小時間尺度變化慢）。

結果：**即使模擬只有 5 步/s，畫面仍然是 60 fps**。

**自動降級**（像遊戲的 dynamic resolution scaling）：幀率 < 30 自動減粒子數，> 55 自動加。這樣使用者根本不用碰「顯示密度」滑桿。

**延遲預算**：總延遲（IPC + 插值 + 顯示）要 < 100 ms 才會覺得跟手。時間插值的 1 幀延遲（16 ms）可接受，但別疊太多層。

### P3.5 健壯性

**JIT 預熱**。首次啟動每個 kernel 要編譯 2–10 秒，`ti.init()` 本身約 1 秒。使用者按下「開始」後卡 10 秒 = 體驗災難。元件載入時就預熱，顯示「編譯中」狀態，並開 `offline_cache=True`。

**發散偵測**。監控 max |u_lattice|，> 0.3 就是要炸了→ 自動降 Δt 或提高 ν 並重啟，告知使用者。不要讓畫面爆成雪花。

**熱啟動**。使用者拖動建築時不重置整場：保留 f 場，只更新 solid 標記。新變固體的格清零，新變流體的格用鄰居的平衡態填入。收斂時間可縮到重跑的 1/5 以下——這是「互動設計」體驗的關鍵。

底層機制就是 P1.4 的「依最大網格配置一次，之後只換內容」。現在養成習慣，到這裡不用改。

## P4 物理可信度

### 問題的核心

建築尺度 Re ≈ 7×10⁶。換算後 τ ≈ 0.5000002——沒有物理黏性，實際的耗散來自**數值誤差**。結果是可能穩定、可能發散，而且**你不知道自己在模擬哪個 Re**。

次網格模型的作用不是把 τ 拉離 0.5（它也拉不遠），而是**在強剪切的地方局部加耗散**——也就是不穩定會起源的地方。

### ❗ 先確認：這個 repo 的 M 矩陣不是教科書版本

實際讀過 `LBM_3D_SinglePhase_Solver.py` 裡的 `M_np` 之後，有一個**必須先搞清楚的分野**：

| 矩陣列 | 標準 d'Humières | 這個 repo | 影響 |
| --- | --- | --- | --- |
| row 1 (e, 能量) | `[-30,-11×6,8×12]` | `[-1,0×6,1×12]` | **不同** |
| row 2 (ε) | `[12,-4×6,1×12]` | `[1,-2×6,1×12]` | **不同** |
| row 9 (3p_xx) | `3e_x²−e²` | `[0,2,2,-1,-1,-1,-1,1×8,-2×4]` | **相同** ✓ |
| row 11 (p_ww) | `e_y²−e_z²` | `[0,0,0,1,1,-1,-1,1×4,-1×4,0×4]` | **相同** ✓ |
| row 13,14,15 | p_xy, p_yz, p_xz | 逐項核對 | **相同** ✓ |

我逐項對過 e 向量驗算了 row 9 與 row 11，確認它們就是標準形式。結論：

### ❗ 修正：結論與我之前寫的相反

我之前寫「能量矩非標準正規化，所以 s_e、s_ε 的文獻值不能套用」。更仔細的分析顯示這個結論是**反的**。

關鍵在於那些非標準的列不是「重新縮放」，而是**與守恆量的線性組合**：

```
row 1  = (11/19)ρ + (1/19) e_std
row 4  = (2/5) j_x + (3/5) q_x
row 10 = (1/3)(3p_xx) + (2/3)(3π_xx)
```

我代入 e 向量驗算過這三列。從這個結構得到三個結論：

1. **row 1、2、4、6、8：文獻鬆弛率可以直接用。** 它們混的是守恆量（ρ 或 j），而守恆量的鬆弛率是 0——混進來的那一部分不會被改變。用 s 鬆弛 `row1` 等價於用同一個 s 鬆弛標準的 `e_std`。
2. **row 9、11、13、14、15：本來就是標準的。** 這一點我之前驗算對了。
3. **真正的限制在三對矩：(1,2)、(9,10)、(11,12)。** row 10 混的是兩個**非守恆**矩。s₉ ≠ s₁₀ 時，在 repo 基底下鬆弛不等價於在標準基底下獨立鬆弛——會多出一個交叉項。

### 這直接影響 LES

現在 s₉ = s₁₀ = `s_v`，所以沒事。但 **LES 會讓 s₉ 逐格變化而 s₁₀ 不變**——這就把交叉項打開了，而且它會**隨空間變化**。結果是 π_xx（一個 ghost 矩）會吃到 (s₁₀−s₉)/2 × (3p_xx)^neq。

黏度仍由 s₉ 決定（標準基底的 row 9 不受影響），所以不致於錯得離譜，但這是一個**沒人驗證過的寄生耦合**。

兩個選項：

- **A（權宜）**：LES 改 s₉ 時也同步改 s₁₀，保持相等。交叉項消失，代價是 π_xx 也被湍流黏度影響（影響小，但不是教科書做法）
- **B（正解）**：先把 M 換成正交 d'Humières 基底，三對矩解開，之後 LES 只動 s₉、s₁₁、s₁₃、s₁₄、s₁₅

**選 B，而且在 P0 就做。** 這與 P0.2 的結論一致，兩個問題指向同一個動作。

這比「整個 M 都不標準」精確，也比「直接照抄文獻」安全。`meq_vec()` 裡 `out[1] = u·u` 就是配合這個非標準 row 1 的，自身一致。

> 若想完全貼文獻，另一個選項是直接把 M 換成標準正交版本並重算 meq。成本不高，而且之後所有文獻都能直接用。建議在 P4 開始前做這個決定。

### P4.1 LES 實作

MRT 加 Smagorinsky 有個漂亮的地方：**應變率張量可以直接從非平衡矩取得**，不用有限差分、不用額外記憶體。`colission()` 裡已經算出 `m_temp - meq` 了，多的成本只有 5 次乘加加一次 sqrt。

```latex
\nu_t = (C_s \Delta)^2 |\bar{S}|, \qquad
|\bar{S}| \propto \frac{\sqrt{\Pi^{neq}_{ij}\Pi^{neq}_{ij}}}{\rho\,\tau}
```

只用 index 9, 11, 13, 14, 15 的非平衡矩組成 Πⁿᵉᵠ。

**只改這五個。** 碰 index 1（bulk）會引入假的體積黏性；碰 ghost modes 更錯。現在的 `S_dig` 把 1, 2, 10, 12 也一起塞了 `s_v`，這幾個要分開處理（P0.2 已經做了一半）。

實作要點：

- `S_dig` 從 `shape=()` 全域向量改成 kernel 內逐格計算（**不需額外記憶體**，只是區域變數）
- C_s ≈ 0.1（壁面流）到 0.17（各向同性湍流），先用 0.1
- 係數換算有多種慣例（Hou et al. 1996 / Krafczyk et al. 2003），**不要憑記憶寫**，對一次原文並用 Taylor–Green 漩流驗證衰減率

### ❗ 修正：WALE 做不到「不用有限差分」

我之前寫「近壁用 WALE 而不是 Smagorinsky + Van Driest damping」，這與同一段的「不用有限差分、不用額外記憶體」**互相矛盾**。

原因：f^neq 的二階矩只給得出**對稱**的應變率張量 S_ij。WALE 的模型需要完整的速度梯度張量 g_ij = ∂u_i/∂x_j，**含反對稱（渦度）部分**——那個資訊不在 f^neq 的二階矩裡。要拿到它就必須做有限差分，而那會增加約 30–50% 的頻寬。

**正確的 P4.1 路線**：

| 模型 | 需要什麼 | 成本 | 何時用 |
| --- | --- | --- | --- |
| **Smagorinsky** | 只要 S_ij，從 f^neq 直接拿 | 幾乎免費 | **先做這個** |
| Smagorinsky + Van Driest | 加一個壁面距離函式 | 低，但要算壁面距離 | 近壁不夠時 |
| WALE | 完整速度梯度，需有限差分 | +30–50% 頻寬 | 前兩者都不夠時才考慮 |

先做 Smagorinsky，量測近壁行為，再決定要不要付 WALE 的代價。**不要一開始就上 WALE**——它還會把 P6 的 kernel 融合變難（有限差分需要鄰居的速度，而融合後速度不落地）。

> 係數換算有多種慣例（Hou et al. 1996 / Krafczyk et al. 2003 的 MRT 版）。**不要憑記憶寫**，對一次原文，並用 Taylor–Green 漩流驗證衰減率。

### P4.2 邊界條件補完

**convective outflow**。現在只有固定壓力，會把擾動反射回來污染結果。尤其在務實版（下游只有 8H）的縮小域下，沒有 convective outflow 就不能縮域。

**地表 wall function**。用對數律從第一層格心外推到 z = 1.5 m。這是**解鎖都市尺度行人風的唯一途徑**，做完之後才能移除 P2.2 的輸出鎖定。

### P4.3 u_lat 提升

從 0.05 提到 0.10，步數直接減半：

### ❗ 修正：u_lat 的限制是局部峰值，不是入流值

我之前寫「入流 u_lat 從 0.05 提到 0.10，Ma 0.15–0.2 之前都是淨賺」——這個建議**漏掉了局部加速**。

建築風場裡，轉角、騎樓下、建築間的缿縮流都會讓局部速度達到入流的 **1.5–2.5 倍**。Ma 約束要看的是那個峰值：

| 入流 u_lat | 局部峰值（1.5–2.5×） | 峰值 Ma | 判定 |
| --- | --- | --- | --- |
| 0.03 | 0.045–0.075 | 0.08–0.13 | ✅ 保守 |
| **0.05** | **0.075–0.125** | **0.13–0.22** | **⚠️ 已在上限** |
| 0.10 | 0.15–0.25 | 0.26–0.43 | ❌ 極易發散 |

**所以入流保持 0.05，不要提到 0.10。** 想要餘裕就降到 0.03–0.04。

這也代表我之前算的「步數減半」不成立：收斂步數維持建築尺度 ~19,000、都市 ~24,000。P5 的時間估算以這組為準。

**要監控的是峰值不是入流**：`get_max_v()` 回傳的就是全域 max |u|，把它除以 cₛ = 0.577 就是實際 Ma。超過 0.25 就要降 u_lat 重跑（這就是 P3.6 發散偵測的門檻來源）。

額外好處：**固定 Re 下提高 u_lat 會讓 ν_lat 等比上升，τ 反而遠離 0.5**。壓縮性變差、τ 穩定性變好，實務上 Ma ≈ 0.15–0.2 之前都是淨賺。風舒適度看的是速度不是壓力，對壓縮性誤差更寬容。

**室內尺度要特別注意**：如果 u_ref 取平均入流 0.3 m/s，但浮力驅動的局部速度可以達 0.6 m/s，u_lat 會悄悄翻倍超過安全區。**室內的 Δt 要用浮力速度尺度而不是平均入流來定。**

## P5 評估模式與氣象校正

### 風向乘數

一次互動模擬 = 一個風向。一張行人風舒適度圖 = **8–16 個方向各自跑到收斂**，再用風玫瑰加權。這把算力預算乘上 8–16 倍。

| 案例 | 單風向 | 16 風向 |
| --- | --- | --- |
| 建築 8.4M（優化後） | 53 秒 | ~14 分鐘 |
| 都市 8.4M | 67 秒 | ~18 分鐘 |
| 都市 100M | ~27 分鐘 | ~7 小時 |

午餐時間跟過夜的差別就在這張表裡。

### P5.1 多風向批次

佇列、進度回報、可中斷可續跑。**結果快取是這裡的關鍵**（套用 P2.4 定好的 hash key）：改一個風向不要重跑全部，改建築高度也只要重跑受影響的那幾個。

這對參數化最佳化特別重要——Galapagos 跑一上午可能要評估幾百個方案，沒有快取就不用玩了。

### P5.2 舒適度評估

風玫瑰加權合成之後，套舒適度準則。兩套的**超越機率閾值不同，要分開實作**，不要想用同一個函式加參數搬完：

| 準則 | 特點 |
| --- | --- |
| **Lawson**（預設） | 按活動類型分級（久坐、逐店、漫步、快走） |
| **NEN 8100** | 荷蘭國標，分級邏輯與閾值不同 |

輸出：分級彩圖 mesh + CSV，可接回 GH 做後續分析。

> Lawson GEM 的峰值因子在文獻上有 1.5–2.0 的差異，實作前先確認你要用哪一版。

### P5.3 氣象資料與校正因子

測站資料**不能直接當基地風速用**。測站通常在機場或開闊地、高度 10 m、地況粗糙度跟基地完全不同。

標準做法是**兩段式地況轉換**（Wieringa）：從測站的 z₀ 用對數律往上推到梯度風高度，再用基地的 z₀ 往下推到參考高度。

```latex
F_{\text{corr}} \;=\; \frac{u_{\text{site}}(z_{\text{ref}})}{u_{\text{met}}(10\,\text{m})}
```

> 中間的混合高度與 potential wind speed 步驟有多套慣例並存，**務必讀原文而不是二手轉述**。

資料來源：

| 來源 | 內容 | 點 |
| --- | --- | --- |
| EPW | 標準格式，直接拿風玫瑰 | 最容易 |
| 中央氣象署觀測資料 | 本地實測 | 格式與 EPW 不同，需轉換層 |
| 手動輸入 | 規範風速、特定情境 | 測試與規範案用 |

**資料來源抽象層**：三者走同一個介面，未來加來源不用改上層。

### 校正 ≠ 驗證

兩件事要分清楚，寫論文時尤其：

|  | 做什麼 | 階段 |
| --- | --- | --- |
| **校正** calibration | 用測站資料設定入流條件 | P5 |
| **驗證** validation | 用基地實測風速比對模擬結果 | 另一個研究題目 |

驗證需要現場量測，不在這份計畫範圍內——但它是這個工具**最有價值的學術輸出之一**。把介面留好，未來接得上。

## P6 效能與記憶體優化

LBM 是純 memory-bandwidth bound，算力完全不是瓶頸。但「搬多少 bytes」要分成**兩個不同的量**，混淆這兩個會導致高估。

### 流量 vs 佔用：一個必須先澄清的帳

D3Q19 不管用幾個陣列，**每 cell 每步都是 19 讀 + 19 寫**。所以：

| 方案 | 流量 B/cell/step | 佔用 B/cell |
| --- | --- | --- |
| **repo 現況（四個 kernel）** | **~488** | 152 |
| f32 融合 collide-stream | 152 | 152 |
| f32 融合 + in-place | 152 | 76 |
| f16 融合 | 76 | 76 |
| f16 融合 + in-place | 76 | 38 |

### ❗ 修正：repo 現況不是 152 B，是約 488 B

我之前把 152 B 當成「現行」——那其實是**理想融合實作**的數字。實際讀完四個 kernel 之後：

| kernel | 讀 | 寫 | floats |
| --- | --- | --- | --- |
| `colission()` | F 19 + rho 1 + v 3 | f 19 | 42 |
| `streaming1()` | f 19 | F 19 | 38 |
| `streaming3()` | F 19 | f 19 + rho 1 + v 3 | 42 |
|  |  | **合計** | **122 × 4 B = 488 B** |

這代表 README 的 900 MLUPS 在 A100-40GB 上是 **439 GB/s ≈ 28% 頻寬利用率**，不是我之前寫的 9%。佈局問題沒有那麼嚴重，**真正的缺口是三次全陣列往返**。

### P6.0（新）kernel 融合——最大的單一收益

這一項我原本完全漏掉了，而它比 SoA 與 FP16 加起來都大。

標準的 LBM 實作把 collision 與 streaming **融成一個 kernel**（fused collide-stream）：讀鄰居的 f 進寄存器 → 算巨觀量 → 碰撞 → 直接寫出。全程 **19 讀 + 19 寫**，rho 與 v 只是寄存器中間值，根本不用落到記憶體（除非要輸出）。

```
488 B → 152 B   即 3.2×，且不動資料佈局、不換精度
```

代價：`Boundary_condition()` 必須整合進去或改成只處理邊界層；debug 難度上升（中間狀態不再落地）。所以要先有 P0 的回歸測試。

### 修正後的 P6 階梯

| 步驟 | 流量 | 累積改善 | 工作量 |
| --- | --- | --- | --- |
| repo 現況 | 488 B | 1.0× | — |
| **+ kernel 融合** | 152 B | **3.2×** | 1–2 週 |
| + SoA 佈局 | 152 B | 改 coalescing 效率，需實測 | 3–5 天 |
| + FP16 | 76 B | **6.4×** | 1–2 週 |
| + in-place | 76 B | 佔用再減半 → 4× 格數 | 2–3 週 |

**順序很重要**：先融合。在四個 kernel 的架構上調 SoA 或 FP16，收益會被全陣列往返淹掉，而你會以為這些技術沒用。

**結論：FP16 是流量槓桿（2×），in-place 是容量槓桿（2×）。** 兩者不是相乘成 4× 吞吐。

in-place 仍然有次要的流量收益（避開另一份目標陣列的 write-allocate、工作集減半讓 L2 重用變好），但這與硬體相關。**量測前不要把它寫進提案。**

實際可期待：約 **2–3× 吞吐 + 4× 格數容量**。這仍然是這個階段最大的收益，只是不是 4×。

### P6.0 SoA 佈局（可能是單一 ROI 最高的改動）

這一項我原本漏掉了，實際讀 code 才浮現。

`ti.Vector.field(19, ti.f32, shape=(nx,ny,nz))` 預設是 **AoS**（array of structs）：同一個 cell 的 19 個分量連續存放。意思是相鄰 thread 讀同一方向的 f 時，位址相距 **76 bytes**——完全無法 coalesce。

SoA（每個方向的 f 跨 cell 連續）才能讓一個 warp 的 32 個 thread 合併成連續讀取。

SoA 改善的是**每一次記憶體存取的效率**，不改變 bytes/cell/step 的理論值。所以它與 kernel 融合是**互補而非替代**：融合減少搬運次數，SoA 讓每次搬運跑滿頻寬。

實測前不要假設收益幅度。先用 `kernel_profiler=True` 量出現在的 achieved bandwidth，再比對改完的值——**這是 CUDA 學習軌 L3 的實驗題目，可以直接拿來用**。

- [ ] 先用 `kernel_profiler=True` 確認目前的實測 MLUPS 與頻寬利用率
- [ ] 改成 19 個獨立 scalar field，或用 `ti.root` 顯式指定 SoA 放置
- [ ] 重測，比對改前改後

> taichi 的 `Vector.field` 預設佈局會隨版本與放置方式變，**實作前先用 profiler 實測確認**，不要假設。

### P6.1 FP16 儲存 / FP32 計算

這是真正的 2× 流量槓桿。儲存用 `ti.f16`，碰撞運算仍用 f32。

對建築風這種不追小數點的用途，精度損失通常可忽略——**但要自己跑一次驗證**（拿 P0 的 benchmark 套件對），不要假設。

> `ti.f16` 的成熟度與各 backend 的支援程度要實測。

### P6.2 In-place streaming

- **AA-pattern**（Bailey 2009）：奇偶步用不同讀寫模式，最簡單，先做這個
- **Esoteric Pull**（Lehmann）：目前已知最好，單陣列 + 隱式 bounce-back + 完美 coalescing，但實作複雜度高一個檔次

主要收益是**佔用減半 → 同顯存能跑兩倍的格數**。流量收益是次要的，要量測才知道。

每一步都要跨 P0 驗證套件確認結果不變——in-place 的 bug 極難找，沒有基準答案你會迷路。

### P6.3 手寫 CUDA

見文件 **04** 的學習軌。**這是學習目標，不是效能瓶頸的解方**——P6.0 到 P6.2 才是。別把它當成必要路徑。

### P6.4 benchmark 方法論

**公平比較的四列矩陣**（避免把演算法改良記在 CUDA 帳上）：

| 版本 | 意義 |
| --- | --- |
| taichi 原始 | 基準線 |
| taichi + SoA + FP16 + in-place | **不換語言就能拿到的改良** |
| CUDA L5 | 換語言的真實價值 |
| CUDA L6 | 加上進階技巧 |

第 1→2 列的差距跟第 2→3 列的差距是完全不同的事。混在一起會導出錯誤決策。

**實測要點**：暖機（丟掉前幾次）、重複多次取中位數、排除 JIT 與首次啟動。用 Nsight Compute 看 achieved occupancy 與 DRAM throughput，判斷是否已接近頻寬上限。

**相容性可能比效能數字更決定性**：CUDA-only 表示使用者必須有 NVIDIA 卡，Mac 出局；而 taichi 有 Vulkan / Metal backend。對一個要給團隊用的工具來說，這件事的權重可能高過 20% 的效能差距。
